# Proposal

## Why

Локальная и продовая БД могут иметь одинаковое физическое имя и похожие схемы разных версий. Сейчас имя одновременно используется для подключения, идентичности каталога, поиска метаданных и маршрутизации SQL: это мешает подключить обе БД и не позволяет безопасно различать окружения одним отображаемым именем.

## What Changes

- Разделить стабильный ID подключения, физическое имя БД и пользовательский ярлык. Поддержать несколько подключений с одинаковым физическим именем; каждому назначать один непустой уникальный ярлык. При отсутствии явного ярлыка использовать физическое имя, только если оно свободно; иначе требовать другой ярлык.
- Показывать ярлыки при выборе источника в UI и предоставить MCP безопасное обнаружение источников и явный выбор. Разрешать выбор ярлыком на внешней границе, но использовать ID во всех внутренних операциях. Переименование ярлыка не меняет ID, историю и принадлежность метаданных.
- Изолировать по ID каталог, анализ схем, SQL-зависимые семантические определения, векторный поиск, сброс/удаление, credentials, кеши и выбор коннектора. Разные версии одноимённых таблиц не должны объединяться; физическое имя остаётся реальным именем для подключения и SQL.
- Зафиксировать один источник на диалог. **BREAKING:** при нескольких доступных источниках новый запрос без выбора отклоняется до генерации/выполнения SQL; автоматический семантический выбор окружения больше не используется. Для единственного источника сохранить автоматический выбор. Продолжение привязанного диалога использует сохранённый ID; смена источника требует нового диалога.
- Сохранить существующие UUID подключений, дочерние записи каталога и доступ к credentials; предусмотреть контролируемую миграцию старых метаданных и env/Vault-конфигураций без угадывания неоднозначного владельца. **BREAKING:** старые диалоги без сохранённого источника доступны только для чтения. Старые обращения по имени продолжают работать только при однозначном разрешении; неоднозначность или недоступность выбранного источника не переключает запрос на другую БД.
- **BREAKING:** унифицировать приоритет конфигурации: непустой `CONNECTION_STRINGS` задаёт активный набор для всех процессов. Сохранённые UI-подключения при этом не удаляются, но не участвуют в выборе и обработке; при снятии env-конфигурации они снова активны.

Межбазовые JOIN, сравнение окружений в одном диалоге, несколько тегов на подключение, новая система прав и автоматическое определение эквивалентности физических серверов не входят в change. Существующие ограничения доступа сохраняются; выбор ID не предоставляет дополнительных прав.

## Capabilities

### New Capabilities

- `database-connections`: стабильная идентичность и ярлыки подключений, согласованное разрешение конфигурации и изоляция жизненного цикла метаданных и credentials при совпадающих физических именах.
- `source-scoped-querying`: обнаружение и явный выбор источника в UI/MCP, сквозное ограничение поиска и SQL одним ID, неизменяемая привязка источника к диалогу и безопасные ошибки выбора.

### Modified Capabilities

Нет: `openspec list --specs --json` не содержит опубликованных capabilities. Существующий код меняет поведение, но ещё не описан основными спецификациями.

## Impact

- Backend: DAL/schema и новые Alembic-миграции; connections/Vault/registry; catalog ingest/diff/reset и SQL-парсинг; semantic compilation/sampling/embeddings; оба pgvector-индекса; retrieval/connector routing; chat/conversation persistence; ingestion API и schedulers.
- Frontend: модель Conversation в Prisma, контракты/маршруты API, формы и карточки подключений, каталог и выбор источника чата, отображение недоступных и legacy-диалогов. Схема `frontend` остаётся под управлением Prisma, не Alembic.
- MCP: discovery только с безопасными полями источника, параметры выбора `ask_question` и согласованная область semantic preflight; регенерация публичного OpenAPI и его копии в MCP, тесты и документация.
- Изменение затрагивает больше восьми файлов и требует согласованного обновления API, ingestion и frontend с миграцией и остановкой старых workers. Новые внешние сервисы, зависимости и credentials не нужны. Эта работа создаёт только планировочные артефакты; миграции, runtime и реализация сейчас не запускаются.
