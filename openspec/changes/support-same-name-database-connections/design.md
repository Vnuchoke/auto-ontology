## Goals / Non-Goals

**Goals:** провести один проверенный source context через существующие модули; сохранить имеющиеся UUID и curated metadata; сделать все потенциально разрушительные операции адресными; подготовить один согласованный релиз с проверяемой миграцией.

**Non-Goals:** отдельная таблица/микросервис connections, подмена физического имени ярлыком, source namespace для каждого общего бизнес-термина, автоматическая миграция неизвестного происхождения данных, изменение имеющихся правил прав или общей политики редактирования endpoint. Изменение endpoint по-прежнему является явной настройкой оператора; автоматическое доказательство тождественности серверов не добавляется.

## Decisions

### 1. Existing catalog UUID is the connection ID

`connection_id` во внешнем контракте равен `catalog_database.id`. Новая отдельная сущность не нужна: подключение и корень каталога уже имеют общий жизненный цикл. `catalog_database.name` остаётся физическим именем и перестаёт быть уникальным **после** перевода всех write paths на ID.

На корне добавить `display_label`, `configuration_origin` (`managed`, `env` или NULL для каталога без активной конфигурации) и nullable `credential_ref`. Ярлык хранится отдельно от `connection` JSON и не поступает в driver options. Для всех корней назначить непустой ярлык; DB check и expression unique index `lower(TRIM(BOTH FROM display_label))` повторяют существующий подход к именам tags в `dal/schema.py`. PostgreSQL-нормализация — единый критерий сравнения; resolver не применяет отличающийся Python casefold. Внешние пробелы удаляются, регистр отображения и Unicode сохраняются. Пустое явно переданное значение — ошибка; отсутствующее значение при создании автозаполняется именем только при свободном ярлыке. Существующий занятый ярлык нельзя автоматически дополнять случайным суффиксом.

Каталог без подключения сохраняет собственный ID, но не становится исполняемым источником. Доступность определяется активной конфигурацией, а не наличием корня. Переименование через connection UI и любой общий catalog patch проходит одну валидацию ярлыка; generic patch не может изменить `id`, `configuration_origin`, `credential_ref` или физическое имя в обход connection lifecycle.

Альтернативы: hostname/имя/ярлык как ключ ломаются при совпадениях или редактировании; дополнительная таблица connections дублирует уже существующий ID.

### 2. One resolver, metadata before credentials

Один resolver в `auto_ontology/connectors/sources.py` возвращает типизированные descriptors: `connection_id`, `display_label`, `database_name`, `dialect`, `configuration_origin`. Он не открывает целевые БД и не читает все Vault secrets. Отдельное получение настроек/коннектора по проверенному ID происходит только для выбранного источника. Ingestion обходит descriptors и открывает их по одному; сбой одного коннектора не меняет identity соседей.

Регистрация env metadata — отдельный write-capable bootstrap в lifespan существующих `server/__main__.py` и `ingestion_service/__main__.py`: после `require_current_schema`, до readiness и запуска chat workers/schedulers. Конкурентные старты сериализуются одной PostgreSQL transaction advisory lock для source registration; внутри неё весь набор проверяется и регистрируется идемпотентно. Ошибка не допускает процесс к readiness и не включает managed fallback. Runtime resolver, GET discovery, coverage и semantic MCP только читают зарегистрированные metadata; отсутствующая регистрация даёт ошибку готовности, а не скрытый upsert. Factory `create_app()` и OpenAPI generation остаются без DB side effects.

Registry и SSO-кеши индексируются ID; создаваемый `SQLDatabase` несёт `connection_id` отдельно от неизменённого смысла `database_name`. Не требуется оборачивать каждый драйвер новым классом. Для запроса сначала проверяются источник и доступ, затем читаются только его credentials и при необходимости обменивается только его SSO-токен. Отказ выбранного источника не запускает перебор других коннекторов.

Подтверждённый приоритет: непустой `CONNECTION_STRINGS` задаёт env-набор всем процессам. Managed-корни сохраняются, но не участвуют в discovery/ingestion/query, пока включён env-режим. Некорректный env-набор — ошибка конфигурации, не разрешение перейти на managed. Настройки env-источников, как и сейчас, не редактируются через UI.

Для env-URL добавить зарезервированные query-поля `metadata_connection_id` и `metadata_label`; resolver удаляет их **до** передачи URL драйверу. Это расширение существующей env-конфигурации, без новых env-переменных. ID — UUID, ярлык кодируется обычным URL encoding. Credentials не сохраняются из env в каталог.

Совместимость plain URL: при миграции принять существующий **catalog-only** корень только при единственном совпадении физического имени, отсутствии managed ownership/credential binding и совместимой конфигурации; сохранить его UUID и зафиксировать env origin. Это контролируемое однократное принятие старой конфигурации, а не общий runtime upsert managed-корня. Existing managed-корень нельзя переводить в env и тем самым терять его активацию после снятия env-режима. Если старый корень может принадлежать обоим способам конфигурации, preflight требует явных раздельных env ID/ярлыка и не угадывает происхождение прежнего каталога. Для нового однозначного plain URL создать и сохранить UUID; последующее разрешение использует его env-корень. При нескольких env-URL с одним физическим именем требуются явные разные ID и ярлыки. После появления нескольких одноимённых корней bare-name привязка становится ошибкой: оператор указывает выданный ID. Порядок URL и пароль не участвуют в идентичности.

Сначала разобрать и проверить весь env-набор, затем транзакционно зарегистрировать его metadata. Повторная регистрация того же набора идемпотентна. Явный ID существующего managed-корня не разрешает переписать его; дубликаты ID, конфликт origin/ярлыка и неоднозначность отклоняют весь набор. При переключении режима корни другой конфигурации не удаляются.

Альтернативы: объединение env/managed добавляет конфликты управления; ID из URL целиком меняется при ротации секрета; ID из позиции меняется при перестановке.

### 3. Explicit credential references, no same-name fallback

Existing Vault-корни получают `credential_ref`, равный **точному прежнему пути**; новые managed-подключения используют путь `connections/<connection_id>`. Переносить или удалять старые Vault secrets при миграции не нужно. Новый источник не пробует legacy path по физическому имени. Inline JSON credentials остаются на своей строке, как и сейчас, если Vault не настроен.

Конфликт ярлыка проверяется до Vault write, окончательно — DB constraint. ID генерируется до Vault write, поэтому секрет нового источника не может перезаписать чужой. После успешного Vault write и неудачной DB insert удаляется только созданный этой попыткой новый ID-path; отказ очистки фиксируется как orphan secret без появления активного подключения. Existing legacy refs не очищаются такой компенсацией. Ошибка чтения настроенного Vault ref не трактуется как разрешение взять inline/соседние credentials. Это необходимое fail-closed изменение существующего широкого `read_secret` fallback.

Connection test при редактировании получает ID, а пустые secret-поля по-прежнему означают сохранение секрета **этого** ID. Label-only edit не требует подключения к БД и не запускает re-ingest. Остальные правила редактирования сохраняются.

### 4. ID-scoped catalog and executable SQL ownership

Передавать source context в catalog model/extract/ingest/write, natural-key registry, parent resolution, incremental diff, parser/schema maps, query matching и model import/export. Database upsert совпадает по ID, schema/table/column keys остаются scoped к parent ID. При данных с несовпадающим ID ссылка отклоняется, а не переназначается по имени.

У `sql_query`, `sql_attribute` и `custom_analysis` добавить ownership `connection_id` с FK на корень. Новые source-bound записи всегда получают ID из проверенного контекста; NULL допускается только для сохранённых legacy-записей с недоказанной принадлежностью и не участвует в query context. Уникальность SQL становится `(connection_id, md5(sql_full_query))`, SQL-атрибутов и custom analyses — `(connection_id, name)`. Дедупликация, счётчики, name conflicts, import matching и ссылки ограничиваются тем же ID. На входе сохранения SQL проверять принадлежность **всех** таблиц/колонок/определений. Глобальный fallback по совпадающему тексту или имени запрещён.

Общие Terms остаются общим словарём; их table/column/SQL отображения проецируются на выбранный ID. Любые SQL-примеры и domain rules, включая `fetch_custom_analyses`, выбираются с source context. Неопределённые legacy SQL definitions доступны для инспекции, но исключены также из prompt, coverage и examples, а не только из непосредственного исполнения. Для shared SQL/attrs со связями нескольких источников миграция выдаёт отчёт, не угадывает принадлежность и не меняет пользовательские определения автоматически.

### 5. Vector identity is a source projection

Обе коллекции получают promoted `connection_id` и индекс для source filters. `database_name` остаётся физическим контекстом, не ключом удаления. Каждая проекция имеет стабильный vector ID, вычисленный стандартным UUIDv5 из `(collection, connection_id, node_id)`; исходный node ID сохраняется в metadata. Повторная запись заменяет эту проекцию, а не добавляет случайный дубль.

Source filter применяется **до построения текста embeddings**, а не только на поиске: bulk semantic embedding не может собрать глобальные attrs/schemas/samples и пометить их выбранным ID. Общий Term имеет отдельную проекцию на каждый связанный источник. Scoped replace/delete принимает `(connection_id, node_id)`; изменение общего vocabulary-поля переиндексирует все его существующие проекции, но строит текст каждой из её собственных source-bound связей. Source reset A не удаляет проекцию B.

**Исключение совместимости — global PQL vocabulary.** `PqlAnalysis` остаётся общим набором few-shot примеров только для генерации PQL; у него нет source/table links и он не участвует в SQL retrieval. Только явно выбранный внутренний PQL-режим VDB может читать/писать/удалять такие записи без connection ID, с обязательным точным фильтром `label = PqlAnalysis`. Он не допускает другие типы узлов, не выполняет global delete коллекции и не ослабляет source checks обычного VDB. Глобальный PQL vector ID использует отдельное стабильное пространство имён, не выдаваемое за ID подключения. Обычные NULL-owned SQL/Term/ColumnAttribute записи не получают такого исключения.

Протянуть ID через `CatalogEmbeddingRowsOp`, semantic row builders, data/semantic VDB factories, metadata reads/edits и refresh paths. Sampling breakers/domain-summary/компиляционные cache keys тоже использовать по ID. Label не включать в embedding text: переименование ярлыка не требует повторных model calls. Физические SQL identifiers остаются прежними.

### 6. Reset keeps identity; connection removal retires it

`dal/reset.py` больше не удаляет зарегистрированный `catalog_database` при сбросе анализа: очищает scoped дочерний каталог и принадлежащие ему executable definitions, затем scoped vectors. Reset всех источников действует так же по каждому корню; identity, origin, credentials и ярлыки сохраняются. Явное окончательное удаление подключения — отдельная операция. Её ID не переиспользуется; история диалогов не каскадируется и не перепривязывается.

Все trigger/proxy/router/scheduler вызовы ingest/reset/semantic compile передают ID. Async-задание захватывает ID до удаления credentials и не разрешает его заново по имени. После частичного сбоя cleanup можно повторить по прежнему ID; повтор не затрагивает новое подключение с таким же ярлыком. Сохраняются существующие семантические правила удаления: общий Term или другая shared-сущность не удаляется, пока нужна соседнему источнику.

### 7. Explicit external contracts with legacy adapters

| Контракт | Решение |
| --- | --- |
| `GET /api/connections/sources` | Новый безопасный discovery: `connection_id`, `display_label`, `database_name`, `dialect`. Доступ через существующий `chat:use`, с действующими ограничениями пользователя; без connection JSON, endpoint, Vault ref и сетевых проб источников. |
| Connection management | Список/create/update возвращают `connection_id` и `display_label` вместе с прежними sanitized полями. Create принимает optional `display_label` рядом с `connection`. Канонические update/delete/SSO paths — `/connections/by-id/{connection_id}` и его `/sso-federation`; прежние name-paths остаются тонкими однозначными adapters к общей логике. Test принимает `replacing_connection_id`; legacy `replacing` остаётся однозначным adapter. |
| Chat и MCP `ask_question` | Optional `connection_id` либо отдельный `connection_label`; одновременно несколько селекторов запрещены. Сохранённый диалог наследует ID. Legacy REST `target_db` принимает UUID/physical name лишь при единственном результате и не трактует label как physical name. После границы state хранит только ID. |
| Coverage/semantic reads | `check_answerable` использует тот же выбор и filter. Semantic tools получают optional source context; source-scoped projections содержат source ID. Чтение общего словаря без source context остаётся обзором, не подбором исполнимых SQL-примеров. |
| Result/SSE | Сохраняются прежние поля ответа; добавляется `source: {connection_id, display_label, database_name}`. MCP `DataAnswer` передаёт provenance без потери существующих SQL/rows. |

MCP curated allow-list дополняется ровно одним `list_sources`, который читает discovery endpoint. Это список источников, не schema/column browsing. Настроить backend/Next/OpenAPI permissions, не открывая settings CRUD пользователям чата. Обновить `frontend/lib/openapiSchemas.ts`, генератор routes и bundled spec MCP через существующие генераторы, а не ручное расхождение JSON.

Для браузерных callers добавить Next proxy routes `frontend/app/api/connections/sources/route.ts`, `connections/by-id/[connection_id]/route.ts` и его `sso-federation/route.ts`. Существующий `[database_name]` route не является catch-all и не проксирует эти пути автоматически. Static `sources`/`by-id` paths регистрируются без затенения legacy adapters.

Ошибки до model/SQL: 422 `source_required`/`invalid_source_selector`, 409 `ambiguous_source`/`source_conflict`/`legacy_conversation_read_only`, 404 для неизвестного или недоступного пользователю ID без раскрытия чужих источников. 503 `source_unavailable`/`source_not_ready` — для временно неисправного выбранного источника; SSO сохраняет существующий отказ авторизации, без downgrade. Конфликт ярлыка — 409. Не возвращать URL или секрет в error details. Существующие legacy routes сохраняют остальные status/response contracts.

Количество источников определяется по активным descriptors после существующей проверки доступа, а не по числу успешно открывшихся коннекторов. Для выбранного source pipeline удаляет автоматический семантический выбор окружения. Валидация зависимостей проверяет ID до генерации/исполнения; одинаковое `database_name` не маскирует межисточниковый запрос.

### 8. Conversation binding is persisted and immutable

В Prisma `Conversation` добавить nullable текстовое `connection_id`; тип соответствует backend catalog ID. Cross-schema FK не добавляется: Prisma владеет только `frontend`, Alembic — схемой Auto Ontology. Источник может быть удалён, а диалог должен сохраниться. Next conversation create по-прежнему может создать пустую строку без ID; authoritative binding выполняет backend при первом вопросе.

В `prepare_conversation` сначала проверить владельца, заблокировать строку existing conversation через `FOR UPDATE` (для конкурентного create — дождаться `ON CONFLICT` и затем читать строку с lock), затем проверить source binding и только после этого читать историю/добавлять вопрос. Пустой диалог без сообщений можно привязать при первом валидном вопросе. Строка с сообщениями и NULL ID — legacy read-only, даже если сейчас подключена одна БД. Несовпадающий явно выбранный ID отклоняется без вставки сообщения. Для bound conversation без селектора берётся сохранённый ID; новый источник в системе не требует повторного выбора.

Проверку активного/разрешённого источника выполнять до начала model work; создание коннектора и SSO — после binding validation. Неверный селектор или конфликт не принимает пользовательский turn. Connection failure после принятия turn остаётся обычной ошибкой выбранного источника; источник не меняется. Межпроцессная неизменяемость обеспечивается DB lock, а не только текущим in-memory slot. Generic PATCH Conversation по-прежнему меняет только title и не принимает `connection_id`.

Устранить второго независимого писателя истории: `frontend/app/api/conversations/[id]/messages/route.ts:27–42` сейчас напрямую делает Prisma insert после owner check. Сохранить этот публичный manual-append route и его право `conversation:write`, но сделать его proxy к backend `POST /api/chat/conversations/{conversation_id}/messages`. Backend counterpart использует тот же transaction/binding protocol в `conversation_dal.py`, что и normal chat; Next больше не вставляет сообщения самостоятельно. Manual append принимает optional `connection_id`/`connection_label`: пустой новый диалог получает source по общим правилам, bound наследует ID, legacy с сообщениями и NULL ID всегда read-only. Explicit conflict отвергается до insert; операция не запускает модель, коннекторы и SSO. Ownership, source validation, insert и обновление conversation timestamp входят в одну транзакцию. История/чарты normal chat сохраняются backend-методами, не через обратный вызов frontend. Гонка manual first append против первого chat question защищена той же строковой блокировкой; общий DAL остаётся единственным писателем, а не дублируется Prisma-реализацией протокола. Новому counterpart сохраняется permission manual route, без расширения до settings CRUD.

В UI показывать selector перед первым вопросом, выбранный ярлык — в header после binding; инициализировать единственный источник автоматически. При нескольких источниках не выбирать первый пункт. Для другого источника кнопка создания нового диалога. В bound chat selector недоступен. Legacy chat показывает read-only banner; удалённый/неактивный source — отдельное состояние недоступности, без автоматического выбора по старому ярлыку. Обновить Prisma selects, REST/types/API/useChat/stream serialization, а не только ChatView.

## Risks / Trade-offs

- [Неполный переход с name на ID] → поведенческие тесты двух одноимённых БД на всех write/read/reset путях; особенно SQL dedup, rules, semantic samples и import matching. Внешнее имя не меняет смысла внутри драйвера.
- [Старые workers пишут name-based данные после миграции] → один согласованный релиз в maintenance window; rolling смешанных версий не поддерживается.
- [Старые semantic vectors уже содержат агрегированный контекст разных БД] → их нельзя признать безопасными только по `database_name`; перестроить source-scoped semantic projections из сохранённых связей. До готовности источник отвечает `source_not_ready`, не выполняет глобальный поиск.
- [Vault и каталог не имеют общей транзакции] → новые уникальные ID-paths, проверка DB uniqueness и узкая компенсация; не переносить/удалять legacy secrets в миграции.
- [Историческое происхождение неизвестно] → пользователь подтвердил read-only legacy chats; SQL metadata с неизвестным владельцем сохраняется для инспекции и исключается из model context до явного исправления.
- [Normalized label collision при обновлении] → preflight выдаёт ID конфликтующих корней; оператор задаёт явный mapping ярлыков до применения unique constraint. Автоматических придуманных ярлыков нет.
- [Снятие env делает часть bound chats неактивной] → ID/history сохраняются; UI показывает недоступность. Возврат того же env-ID возобновляет доступ, а не создаёт новую привязку.

## Migration Plan

Все действия ниже — будущие implementation/release steps, не разрешение выполнять миграции сейчас.

1. **Preflight и backup.** На копии store собрать отчёт по existing catalog IDs, origin, нормализованным ярлыкам, Vault references и ownership SQL/vector записей. Добавить в реализации один идемпотентный helper `dev_tools/migrate_connection_identity.py`: `--check` только читает/выдаёт безопасный отчёт; `--apply` делает проверенный backfill; `--mapping <path>` принимает JSON mapping ID → `{display_label, configuration_origin, credential_ref}` с явными решениями оператора для конфликтов. Mapping не содержит secret values. Автоматический origin допустим для однозначного inline managed либо env-only catalog root; Vault-managed ownership подтверждается известным legacy reference, не догадкой по NULL connection. Неопределённый origin блокирует активацию такого источника до mapping. Сначала вручную проверить одну fixture-запись, затем доказать повторяемость helper тестом. Проверить backup store, vector schemas и frontend data. Не читать и не копировать содержимое Vault secrets для определения identity.
2. **Остановить старых писателей.** Остановить API/chat workers, ingestion и semantic schedulers; не допускать mixed-version записей. Зафиксировать одинаковую env-конфигурацию процессов. Эта операция и любые реальные production/Vault действия требуют отдельного разрешения оператора.
3. **Добавить схемы.** Новые Alembic revisions, сгенерированные от `dal/schema.py`, добавляют root metadata и SQL ownership без изменения существующих IDs; отдельный Prisma schema push добавляет nullable `frontend.conversations.connection_id`. Изменения применяются только к своим схемам. Векторные таблицы управляются существующим VDB-кодом, не SQLAlchemy METADATA: helper добавляет `connection_id`/индекс/стабильные projection IDs в уже существующие коллекции, а VDB init создаёт такую же схему для новых. Отсутствующие коллекции допустимы и не создаются с неизвестной размерностью.
4. **Backfill.** Ярлыки — physical name либо approved mapping, origin — по настроенному способу конфигурации, Vault ref — прежний точный путь. Сохранить root/child IDs и descriptions. SQL ownership выводить из полного набора связанных таблиц/колонок; единственный владелец backfill, несколько/ни одного — NULL плюс отчёт, исключение из source-scoped reads. Data vectors связывать прежде всего по node ID и catalog ancestry; только при отсутствии доказанного ID допустимо однозначное старое имя при отсутствии противоречащих ссылок. Неразрешённые строки оставить вне исполнения. Shared semantic Terms не назначать одному источнику по node ID; построить отдельные проекции из их scoped связей и заново вычислить semantic embeddings существующим embedder. До этой готовности не включать retrieval источника; не переиспользовать потенциально смешанный старый semantic text.
5. **Проверить и активировать один релиз.** `--check` должен подтвердить labels/IDs/ownership и отсутствие исполняемых неразрешённых записей. Source-aware код — единственные новые писатели. Только после этого снять уникальность physical name, включить новый API/UI/MCP и разрешить создание одноимённых подключений. Запустить source-scoped проверки; неготовый source остаётся недоступным для SQL. Plain env с неоднозначностью получает требование явных ID/labels, а не новый случайный источник. Backfill повторяется без смены IDs и без повторных дублей проекций.
6. **Rollback.** До допуска дублирующих физических имён и новых source-scoped записей можно восстановить backup и прежний комплект сервисов. После появления дубликатов downgrade к name-based коду небезопасен: остановить writers и восстановить согласованный pre-upgrade backup всех трёх областей (catalog, vectors, frontend) либо выполнить forward fix. Не удалять/сливать новые источники и не отбирать произвольного владельца ради прохождения старого constraint. Vault legacy paths остаются нетронутыми; cleanup новых ID-paths — отдельная адресная операция с разрешением, не массовое удаление.

## Verification Strategy

Перед каждым нетривиальным изменением написать поведенческий тест и получить ожидаемый red на текущем коде; затем минимальный green и проверка совместимости. Использовать две изолированные тестовые БД с именем `sales`, одноимённой `public.orders`, различающимися колонками и значениями-маркерами; не production. Для unit tests — fakes/spies коннекторов и store, для финального integration — disposable Postgres/pgvector и отдельная frontend schema. Внешние LLM/embedding вызовы в автоматических тестах подменять детерминированным adapter; реальная ручная проверка только с разрешённой локальной средой.

Матрица: создание/rename/collision/concurrent label writes; старые IDs и env reorder/secret rotation; приоритет env; exact credential ref и сбои Vault; selected-only SSO; ingest/diff/reset/delete/повтор cleanup A без изменений B; одинаковые SQL/names и cross-source links; shared Term projection/update/reset; data+semantic vector backfill и повтор; selectors/coverage/physical SQL qualifiers; 0/1/2 источника и unavailable сосед; provenance SSE/MCP; bound/legacy/deleted/empty/racing conversations и ownership denial. Проверить обычный single-source workflow и существующие tests, а не только новый сценарий.

Команды implementation-проверок: backend `uv run pytest auto_ontology dev_tools -q`, `uv run ruff check auto_ontology/ dev_tools/` и `uv run ruff format --check auto_ontology/ dev_tools/`; отдельно из `mcp/` — `uv run pytest tests -q`. Из `frontend/` — `pnpm exec vitest run api/chat.test.ts api/conversations.test.ts 'app/api/conversations/[id]/messages/route.test.ts'`, `pnpm format:check`, `pnpm lint`, `pnpm build`. Указанные frontend test-файлы — новые задачи реализации, не существующие проверки; для alias `@/` задать минимальный `vitest.config.ts` с разрешением к frontend root средствами уже установленного Vitest/Vite, без новых plugins/dependencies. Генерация контрактов: `uv run python -m dev_tools.generate_backend_openapi`, затем из frontend `pnpm openapi`; проверить все изменённые JSON и bundled MCP spec. Без установки новых инструментов; доступные crapper/dryer/mutator применять при реализации, отсутствие явно отметить. Prisma push/Alembic/backfill и destructive tests запускать только на разрешённой disposable базе; `start`/`db:push` не использовать как безусловную read-only проверку.

Сейчас проверяется только согласованность планировочных artifacts, их review и `openspec validate --strict`. Реализация начинается лишь отдельным `/opsx-apply`.
