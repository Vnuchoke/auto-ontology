# Spec Delta

## Purpose

Обеспечивать явный и проверяемый выбор анализируемого источника в UI и MCP, чтобы контекст, SQL и история диалога не переходили между одноимёнными БД и разными окружениями.

## ADDED Requirements

### Requirement: Safe source discovery
UI и MCP SHALL предоставлять авторизованному пользователю список активных источников с ID, ярлыком и физическим именем. Обнаружение SHALL сохранять действующие ограничения доступа и MUST NOT возвращать credentials, connection strings или Vault references. Получение списка MUST NOT требовать открытия всех целевых БД.

#### Scenario: Discover two same-name databases
- **WHEN** пользователь или MCP-агент получает список активных источников
- **THEN** локальная и продовая БД `sales` представлены разными ID и ярлыками
- **AND** в ответе нет секретов и параметров доступа

#### Scenario: Unrelated source is offline
- **WHEN** один из зарегистрированных источников недоступен по сети
- **THEN** список источников остаётся доступным без подключения к этой БД
- **AND** недоступность соседа не блокирует выбор исправного источника

### Requirement: Explicit source selector
UI SHALL показывать ярлык и передавать выбранный ID. MCP SHALL принимать явный ID либо отдельный параметр ярлыка. Система SHALL разрешать ярлык в один ID до поиска и SQL; конфликтующие селекторы и неизвестные значения SHALL отклоняться без fallback. ID MUST NOT трактоваться как физическое имя или ярлык.

#### Scenario: Select a source by label through MCP
- **WHEN** запрос MCP указывает ярлык `sales-local`
- **THEN** он разрешается в текущий ID этого источника
- **AND** дальнейшая обработка использует ID, а не ярлык как ключ

#### Scenario: Unknown or conflicting selector
- **WHEN** задан неизвестный ID, неизвестный ярлык либо одновременно несколько видов селектора
- **THEN** запрос отклоняется до семантического поиска и генерации SQL
- **AND** единственный или наиболее похожий другой источник не подставляется

### Requirement: No implicit multi-source query selection
Для нового диалога и запроса без истории при нескольких активных доступных пользователю источниках система SHALL требовать явный выбор до поиска, генерации и выполнения SQL. При ровно одном источнике отсутствие выбора SHALL означать его автоматический выбор. Недоступный источник MUST NOT исключаться из подсчёта только ради выбора другого.

#### Scenario: Multiple sources without selection
- **WHEN** доступны два источника, а новый запрос не указывает источник
- **THEN** возвращается ошибка необходимости выбора
- **AND** SQL не генерируется и ни один коннектор не исполняет запрос

#### Scenario: One configured source
- **WHEN** доступен ровно один активный источник и новый запрос не указывает источник
- **THEN** система выбирает его ID и явно сообщает использованный источник в результате

#### Scenario: One of two sources is unhealthy
- **WHEN** зарегистрированы два активных источника и один временно недоступен
- **THEN** запрос без выбора всё равно требует явного выбора
- **AND** ошибка выбранного неисправного источника не переключает запрос на исправный

### Requirement: One source throughout query processing
Система SHALL ограничивать выбранным ID семантическую проверку покрытия, retrieval, примеры и правила для модели, SQL-зависимости, выбор диалекта и выполнение SQL. Данные другого источника MUST NOT попадать в контекст только из-за совпадения имён, общего термина или текста SQL. Результат SHALL содержать ID, ярлык и физическое имя использованного источника.

#### Scenario: Similar schemas produce different answers
- **WHEN** запрос направлен в `sales-local`, а в обеих БД есть одноимённые таблицы с разными контрольными значениями
- **THEN** модель получает только локальные source-bound определения и структуру
- **AND** SQL выполняется только локальным коннектором и возвращает локальное контрольное значение
- **AND** ответ содержит локальный ID и ярлык

#### Scenario: Shared glossary term
- **WHEN** общий термин имеет отображения в локальной и продовой БД, а preflight и запрос выбрали локальный ID
- **THEN** coverage, примеры, выражения и samples относятся только к локальным отображениям этого термина

#### Scenario: Global PQL examples remain separate from SQL context
- **WHEN** подсистема генерации PQL обращается к общим `PqlAnalysis` few-shot примерам
- **THEN** она использует явно выбранный внутренний global PQL режим с точным фильтром типа
- **AND** исключение не разрешает SQL retrieval, другим semantic-узлам или source reset читать, записывать либо удалять данные без выбранного ID источника

### Requirement: Selected source is resolved before credentials and execution
Обработка запроса SHALL открывать credentials, обменивать SSO-токен и создавать исполняющий коннектор только для выбранного источника. Ошибка выбранного источника SHALL завершать запрос без переключения источника или режима авторизации.

#### Scenario: Local query does not authenticate to production
- **WHEN** выбран локальный источник, а продовый источник требует SSO или недоступен
- **THEN** локальный запрос не читает продовые credentials и не обменивает продовый SSO-токен
- **AND** состояние продового источника не мешает локальному запросу

### Requirement: Immutable conversation source
Новый диалог SHALL сохранять выбранный ID до принятия первого вопроса и загрузки истории. Последующие вопросы SHALL наследовать этот ID; другой явно указанный ID SHALL отклоняться с предложением нового диалога. Проверка владельца и неизменяемость привязки SHALL действовать также при конкурентных запросах.

#### Scenario: Continue a bound conversation
- **WHEN** следующий вопрос содержит ID существующего диалога и не содержит нового селектора источника
- **THEN** используется сохранённый ID источника, даже если активных источников стало больше
- **AND** переименование ярлыка не изменяет привязку диалога

#### Scenario: Attempt to switch source
- **WHEN** диалог привязан к локальному ID, а новый вопрос явно указывает продовый ID
- **THEN** запрос отклоняется до добавления вопроса и запуска модели
- **AND** существующая история и привязка не изменяются

#### Scenario: Concurrent first questions
- **WHEN** два первых запроса пытаются привязать один новый диалог к разным источникам
- **THEN** диалог получает не более одной привязки
- **AND** запрос с другим ID не получает чужую историю и не выполняет SQL

### Requirement: Read-only legacy and unavailable-source conversations
Диалоги с историей, но без сохранённого ID источника SHALL оставаться доступными только для чтения. Если источник привязанного диалога удалён, отключён конфигурацией или недоступен пользователю, новые вопросы SHALL отклоняться без перепривязки; история SHALL сохранять действующие правила доступа.

#### Scenario: Legacy conversation has no source provenance
- **WHEN** пользователь открывает старый диалог без ID источника
- **THEN** сообщения доступны для чтения и интерфейс предлагает новый диалог с выбором источника
- **AND** попытка продолжения через UI или MCP отклоняется даже при одном текущем источнике

#### Scenario: Manual message append cannot bypass read-only history
- **WHEN** API-клиент пытается вручную добавить сообщение в legacy-диалог без сохранённого источника
- **THEN** добавление отклоняется даже при переданном новом селекторе источника
- **AND** история и её отсутствие source binding остаются неизменными

#### Scenario: Reused label after source deletion
- **WHEN** источник диалога удалён, а его ярлык присвоен новому подключению
- **THEN** диалог не начинает использовать новое подключение
- **AND** запросы к прежнему диалогу возвращают ошибку отсутствующего источника

### Requirement: Unambiguous legacy selectors
Существующий селектор физического имени SHALL поддерживаться только при однозначном соответствии активному источнику. Неоднозначный legacy-селектор SHALL отклоняться с требованием ID или ярлыка; порядок конфигурации, совпадение регистра и сходство схем MUST NOT выбирать окружение за пользователя.

#### Scenario: Legacy name is still unique
- **WHEN** старый API-клиент указывает физическое имя и ему соответствует ровно один активный источник
- **THEN** запрос разрешается в его стабильный ID и далее выполняется source-scoped

#### Scenario: Legacy name becomes ambiguous
- **WHEN** старый API-клиент указывает `sales`, а активны локальная и продовая БД с этим именем
- **THEN** возвращается ошибка неоднозначного источника без выполнения SQL

### Requirement: Cross-source SQL is rejected
Система MUST NOT выполнять один SQL-запрос, чьи разрешённые зависимости относятся к разным ID источников. Совпадающие физические имена MUST NOT скрывать такое смешение; изменение маршрута на первый найденный коннектор запрещено.

#### Scenario: Mixed same-name table dependencies
- **WHEN** SQL или выбранное исполнимое определение ссылается на таблицы локального и продового ID
- **THEN** запрос отклоняется как межисточниковый
- **AND** ни один коннектор не выполняет SQL
