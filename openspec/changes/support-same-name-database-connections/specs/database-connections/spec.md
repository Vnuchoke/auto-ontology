# Spec Delta

## Purpose

Различать анализируемые БД независимо от совпадения физических имён, сохраняя стабильную идентичность подключения и изолируя его метаданные, credentials и жизненный цикл.

## ADDED Requirements

### Requirement: Stable connection identity
Система SHALL назначать каждому зарегистрированному источнику стабильный уникальный ID, независимый от физического имени, ярлыка, порядка конфигурации и секретов. Совпадение физических имён MUST NOT объединять подключения.

#### Scenario: Same physical database name on different servers
- **WHEN** зарегистрированы локальная и продовая БД с физическим именем `sales` и разными ярлыками
- **THEN** система хранит два разных ID и два независимо выбираемых подключения
- **AND** физическое имя обеих БД остаётся `sales`

#### Scenario: Identity survives maintenance
- **WHEN** изменён ярлык, ротированы credentials или перезапущены процессы
- **THEN** ID подключения и принадлежность его каталога остаются прежними

### Requirement: Required unique human-readable label
Каждое подключение SHALL иметь один непустой пользовательский ярлык. Система SHALL убирать внешние пробелы и обеспечивать уникальность ярлыков без учёта регистра среди зарегистрированных подключений, включая конкурентные записи. Отсутствующий ярлык SHALL заполняться физическим именем только при отсутствии конфликта.

#### Scenario: Default label is free
- **WHEN** создаётся подключение к `sales` без явного ярлыка и этот ярлык свободен
- **THEN** подключение получает ярлык `sales`

#### Scenario: Default or explicit label conflicts
- **WHEN** ярлык `sales` уже занят и новое подключение не задаёт другого ярлыка либо задаёт ` Sales `
- **THEN** сохранение отклоняется с сообщением о конфликте ярлыка
- **AND** существующее подключение и его credentials не изменяются

#### Scenario: Concurrent label creation
- **WHEN** две операции одновременно сохраняют одинаковый нормализованный ярлык
- **THEN** не более одной операции завершается созданием подключения
- **AND** другая получает контролируемую ошибку конфликта без перезаписи чужих данных

### Requirement: Label is not a routing or SQL identity
Система SHALL позволять переименование ярлыка без смены ID, повторного анализа и перепривязки диалогов. Ярлык MUST NOT подменять физическое имя в параметрах драйвера или квалификаторах SQL.

#### Scenario: Rename an already analyzed source
- **WHEN** ярлык источника меняется с `sales-local` на `Локальные продажи`
- **THEN** списки выбора показывают новый ярлык для того же ID
- **AND** сохранённый диалог и метаданные по-прежнему относятся к этому ID
- **AND** сгенерированный SQL использует реальные имена БД, схем и таблиц, а не ярлык

### Requirement: Source-owned catalog and executable metadata
Анализ и поиск SHALL различать схемы, таблицы, колонки и исполнимые SQL-определения по ID источника. Совпадающие имена и текст SQL MUST NOT автоматически объединять такие записи разных источников. Общий бизнес-термин SHALL возвращать только относящиеся к выбранному источнику отображения и выражения при source-scoped чтении.

#### Scenario: Different schema versions with the same object names
- **WHEN** обе БД содержат `public.orders`, но только локальная версия имеет колонку `draft_status`
- **THEN** каждая таблица и её колонки принадлежат своему источнику
- **AND** метаданные продовой таблицы не содержат локальную колонку

#### Scenario: Identical SQL definitions in two sources
- **WHEN** одинаковый текст SQL и одинаковое имя SQL-атрибута сохранены независимо для двух источников
- **THEN** определения сохраняют раздельную принадлежность, зависимости и изменения
- **AND** обновление одного определения не меняет выражение и зависимости другого

### Requirement: Credentials are bound to a connection
Чтение, обновление, тестирование и удаление credentials SHALL относиться к выбранному ID. Новый одноимённый источник MUST NOT читать или перезаписывать legacy-секрет другого подключения. Недоступность credentials SHALL быть ошибкой выбранного источника, а не причиной использовать соседнее подключение или иной режим авторизации.

#### Scenario: Existing Vault secret and new same-name source
- **WHEN** старый источник использует сохранённый секрет для `sales`, а новый источник имеет такое же физическое имя
- **THEN** старый источник сохраняет доступ к своему секрету
- **AND** новый источник использует только собственную привязку credentials

#### Scenario: Selected source credentials cannot be read
- **WHEN** секрет выбранного источника недоступен или обмен SSO-токена не удался
- **THEN** его операция завершается контролируемой ошибкой
- **AND** credentials другого источника и fallback на сохранённый токен вместо обязательного SSO не используются

### Requirement: Isolated ingest reset and deletion
Повторный анализ, семантическая компиляция, адресный сброс, обновление embeddings и удаление SHALL изменять только выбранный источник. Сброс анализа SHALL сохранять ID существующего подключения. Окончательное удаление MUST NOT переназначать его ID другому подключению или диалогу.

#### Scenario: Reset one of two same-name sources
- **WHEN** сбрасываются каталог или векторные записи локального источника
- **THEN** продовый каталог, его SQL-зависимости, credentials и оба вида embeddings остаются неизменными
- **AND** повторный анализ локального источника использует его прежний ID

#### Scenario: Delete and recreate a source
- **WHEN** подключение удалено и затем создано новое с тем же ярлыком и физическим именем
- **THEN** новое подключение имеет другой ID
- **AND** прежние диалоги не переходят на новое подключение

#### Scenario: Retired identity cannot be resurrected
- **WHEN** после окончательного удаления env registration, model import либо запоздалый ingest пытается создать root с прежним ID
- **THEN** application writer отклоняет повторное использование ID до создания root
- **AND** запись retirement сохраняется после обычного и глобального reset
- **AND** новый ID может использовать освобождённый ярлык без перепривязки старой истории

#### Scenario: Shared term has two vector projections
- **WHEN** общий термин представлен в двух источниках и обновляются или сбрасываются embeddings одного источника
- **THEN** изменяется только проекция этого термина в выбранном источнике
- **AND** проекция другого источника сохраняет свои schema context и samples

### Requirement: Consistent configured source identities
API, ingestion и семантическая компиляция SHALL использовать одинаковый набор активных источников и их ID. Env-конфигурация SHALL сохранять идентичность после перестановки URL и ротации секретов; неявная привязка по физическому имени допустима только при однозначности. Некорректная активная конфигурация MUST NOT молча переключать процессы на другой набор источников.

#### Scenario: Legacy environment configuration
- **WHEN** существующий env-URL без явного ID однозначно соответствует зарегистрированной БД
- **THEN** API и ingestion используют её сохранённый ID и один ярлык
- **AND** ротация пароля или перестановка URL не создаёт новую идентичность

#### Scenario: Same-name environment sources
- **WHEN** env-конфигурация содержит два источника с физическим именем `sales`
- **THEN** каждый имеет явную раздельную привязку ID и уникальный ярлык
- **AND** неоднозначная конфигурация отклоняется до анализа и SQL, а не схлопывается по имени

### Requirement: Environment configuration takes precedence
При непустом `CONNECTION_STRINGS` все процессы SHALL использовать только env-источники. Сохранённые UI-подключения SHALL оставаться неизменными и неактивными до удаления env-конфигурации. Регистрация env-набора SHALL быть атомарной: конфликт ID или ярлыка MUST NOT частично переписать существующие подключения.

#### Scenario: Both configuration methods are present
- **WHEN** заданы env-источники и ранее сохранены UI-подключения
- **THEN** discovery, запросы и анализ используют только env-набор
- **AND** после удаления env-конфигурации доступны прежние UI-подключения с прежними ID

#### Scenario: Invalid environment registration
- **WHEN** в одном env-наборе есть конфликт ID или ярлыка
- **THEN** весь новый набор отклоняется без частичной регистрации
- **AND** система не переключается на UI-набор и не раскрывает connection strings в ошибке

### Requirement: Non-destructive identity migration
Обновление SHALL сохранять существующие ID подключений и дочерних записей, пользовательские метаданные и доступ к credentials. Владельцы старых индексных и SQL-зависимых записей SHALL назначаться только при доказуемом соответствии; неоднозначные записи SHALL оставаться доступными для инспекции, но не для source-scoped исполнения до исправления.

#### Scenario: Unambiguous existing connection
- **WHEN** выполняется миграция подключения с уникальным физическим именем
- **THEN** его ID, дочерние ID, описания и настройки сохраняются
- **AND** начальный ярлык равен физическому имени при отсутствии конфликта
- **AND** табличный индекс с доказуемым владельцем получает тот же ID без обязательного повторного обращения к embedding-модели

#### Scenario: Ownership or normalized labels are ambiguous
- **WHEN** миграция обнаруживает неоднозначное происхождение записей либо конфликт начальных ярлыков
- **THEN** система выдаёт отчёт без секретов и не угадывает владельца или пользовательский ярлык
- **AND** конфликтующие данные не удаляются автоматически
- **AND** неоднозначные записи не попадают в исполнение запросов
